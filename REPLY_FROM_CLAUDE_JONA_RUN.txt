Things to know (each one cost us time today)
1. Pages are static. The frontend container runs `astro build` ONCE at start, from the backend's
   data. Menus that arrive later (MCP scraper incl. the 06:00 job, ETH/UZH import every 6 h) only
   show after `docker compose restart frontend`. The API has them immediately.
   Details and a suggested periodic-rebuild fix: NOTE_FOR_GERGO_MENUS.txt.
2. Scraping with MEAL_SCRAPER_ENABLED=true starts by itself on backend startup (missing venues).
   A manual POST /api/scraped-menus/refresh during that run returns 409 {"status":"already_running"};
   wait until /api/scraped-menus says running=false, then trigger the full refresh (202 "started").
   Our run: about 4 min for the startup pass + 3 min for the full refresh; 27 of 39 venues with
   results, 12 with status source_unavailable (no verified URL in mensa/scraper-locations.json).
   Afterwards we set MEAL_SCRAPER_ENABLED back to false (only via a one-off shell variable for that
   run) to avoid further paid calls from the 06:00 job and from cache misses.
   Note: our run used the scraper model from our .env copied before your change, so gpt-5-mini
   (current .env.example default) is untested here.
3. Windows checkouts (core.autocrlf=true): frontend/scripts/container-entrypoint.sh gets CRLF; the
   frontend Dockerfile strips it since bd06a90. Without that the container restart-loops with
   "set: illegal option -". Your meal-scraper Dockerfile already did the same.
4. Checking pages with curl: /canteen/<id> answers 308 to /canteen/<id>/; use -L, otherwise the page
   looks empty.
5. Login: since 8b0f757 there is no login UI and no identity configuration for local runs; nothing to set.
6. The internal API (INTERNAL_API_ENABLED) stays off in Compose; it is not needed to run or refresh.

If something in the stack fails on your side, put the `docker compose logs --tail=100 <service>`
output into a txt note; we watch the repo for notes addressed to Claude.
